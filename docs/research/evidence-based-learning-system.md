# Corthex Classmate — 근거 기반 학습 시스템 설계

> 조사 기준일: 2026-09-01 KST  
> 목적: 하루 최대 8교시의 Java·Spring 수업을 **놓치지 않고 따라가며**, 수업 뒤에는 **AI 없이도 설명·추적·수정·구현**하도록 돕는 제품 정책을 정한다.

## 결론

**Corthex Classmate는 “수업을 대신 요약하는 AI”가 아니라, 수업 중에는 조용히 맥락을 보존하고 수업 뒤에는 사용자가 직접 기억을 꺼내고 코드를 다루게 하는 학습 동반자로 만들어야 합니다.**

- 라이브 모드: 평소에는 조용히 기록하고, 사용자가 부를 때만 **한 문장 결론**을 먼저 준 뒤 즉시 수업으로 돌려보냅니다.
- 교시 직후: 요약을 먼저 보여 주지 않고 **핵심 한 문장·값 하나 추적·남은 질문 하나**를 사용자가 먼저 답합니다.
- 복습 모드: `완성 예제 → 예측·추적 → 빈칸·재배열 → 수정·디버깅 → 독립 작성 → 다음 날 재현` 순으로 AI 도움을 줄입니다.
- 성공 판단: 노트 분량이나 대화 시간이 아니라 `예측 → 값 추적 → 이유 설명 → 도움 없이 비슷한 기능 작성 → 다음 날 다시 해냄`으로 측정합니다.

이 방향은 강한 연구 근거에 맞지만, **이 제품 자체의 성능이 보장되었다는 뜻은 아닙니다.** 380px 패널, Tiro·Meet·IntelliJ 문맥 결합, 하루 8교시 피로도는 실제 2주 PoC로 검증해야 합니다.

## 1. 다른 세션과의 역할 경계

참조한 Codex 작업 `Design integrated coding study path`는 완성 결과에서 출발해 Java → MySQL → JDBC를 하나의 프로젝트 흐름으로 배우는 **학습 경로**를 설계하고 있습니다.

이 문서는 그 경로를 다시 만들지 않습니다. 두 작업은 다음처럼 연결합니다.

| 작업 | 맡는 문제 | 공통으로 확인할 성취 |
|---|---|---|
| 통합 코딩 학습 경로 | 무엇을 어떤 프로젝트 순서로 배울까? | 예측·추적·설명·독립 구현·다음 날 재현 |
| Corthex Classmate | 수업 중 막힌 순간을 어떻게 회복하고, 언제·어떻게 다시 연습할까? | 예측·추적·설명·독립 구현·다음 날 재현 |

```text
통합 코딩 학습 경로
  └─ 오늘 배울 프로젝트 조각과 난이도
                 │
                 ▼
Corthex Classmate
  ├─ 라이브 수업 문맥 보존
  ├─ 막힌 순간의 최소 설명
  ├─ 교시 직후 회상
  ├─ 코드 추적·수정·디버깅 연습
  └─ 다음 날 독립 재현 확인
```

따라서 학습 경로가 “무엇”을 정하면 Classmate가 “그것을 실제로 배우게 하는 시간·도움·검증 방식”을 맡습니다.

## 2. 왜 “좋은 요약 앱”만으로는 부족한가

### 2-1. 읽을 때 이해되는 느낌과 혼자 해내는 능력은 다릅니다

STEM 분야 225개 연구를 모은 메타분석에서는 능동학습이 전통 강의보다 시험·개념검사 성과를 평균 0.47 표준편차 높였고, 전통 강의 집단의 실패 가능성이 더 높았습니다. 또 다른 무작위 비교에서는 능동적으로 공부한 학생이 실제로 더 배웠지만 **덜 배운 것처럼 느끼기도** 했습니다. 즉, “설명이 매끄럽다”와 “나중에 혼자 해낸다”를 구분해야 합니다. [Freeman et al. 2014](https://doi.org/10.1073/pnas.1319030111), [Deslauriers et al. 2019](https://doi.org/10.1073/pnas.1821936116)

그래서 Classmate의 요약은 다음 역할만 맡습니다.

- 수업 내용을 찾는 지도
- 선생님 말·화면·코드로 돌아가는 근거 색인
- 다음에 직접 해볼 행동을 고르는 출발점

요약을 읽었다는 사실만으로는 “학습 완료”가 되지 않습니다.

### 2-2. AI는 연습 중 정답률을 높여도 독립 수행을 약화시킬 수 있습니다

약 1,000명의 고등학생이 참여한 수학 연구에서는 범용 GPT가 연습 중 성과를 높였지만, AI를 제거한 뒤에는 무AI 대조군보다 성적이 낮아졌습니다. 교사가 설계한 힌트 중심 GPT Tutor는 이 손실을 크게 완화했습니다. 핵심은 “AI 사용 여부”보다 **답을 대신했는지, 생각을 돕도록 제한했는지**입니다. [Bastani et al. 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC12232635/)

반대로 194명이 참여한 대학 물리 실험에서는 고도로 설계된 AI 튜터가 능동수업보다 높은 짧은 학습 성과를 보였습니다. 그러나 이 시스템은 전문가가 만든 자료·단계별 정답·영상·순서 제어를 갖춘 전용 플랫폼이었습니다. 일반 채팅창에 긴 프롬프트 하나를 넣은 결과가 아닙니다. [Kestin et al. 2025](https://www.nature.com/articles/s41598-025-97652-6)

따라서 Classmate는 “좋은 프롬프트 모음”이 아니라 **순서와 도움의 양을 통제하는 상태형 앱**이어야 합니다.

### 2-3. 라이브 수업에서는 AI도 주의 분산이 될 수 있습니다

27개 무작위 실험을 모은 2025년 메타분석에서는 모바일 주의 분산이 즉시 회상과 강의 회상을 크게 낮추는 방향이었습니다. 이것이 AI 사이드패널의 효과를 직접 측정한 것은 아니지만, 라이브 UI가 또 하나의 강의처럼 말하면 위험하다는 강한 경고입니다. [Mobile distraction meta-analysis 2025](https://www.sciencedirect.com/science/article/pii/S0747563224003005)

그러므로 제품의 기본값은 다음과 같습니다.

```text
계속 설명하는 AI     ✕
계속 퀴즈를 띄우는 AI ✕
알림이 쌓이는 AI      ✕

조용히 문맥을 잡는 AI ✓
사용자가 부를 때 한 문장으로 돕는 AI ✓
수업이 끝난 뒤 능동 연습을 여는 AI ✓
```

## 3. 전체 학습 루프

### 표기 범례

- `[ ]`: 그 시점에 저장되는 상태
- `→`: 다음 행동
- `◇`: 사용자의 선택 또는 수행 결과

### 시간 흐름 순서도

```text
수업 전 60초
[오늘의 연결고리 2개]
        │
        ▼
라이브 60분
[전사 + Meet 장면 + IntelliJ 문맥]
        │
        ├─ 이해됨 ───────────────────────────────┐
        │                                        │
        └─ 막힘 → 질문 시점 봉인 → 한 문장 답 ──┤
                                                 │
                                                 ▼
교시 직후 3분
요약을 가린 채 회상
  1. 핵심 한 문장
  2. 값 하나 추적
  3. 남은 질문 하나
        │
        ▼
◇ 제대로 설명·추적했나?
  ├─ 예 → 다음 교시 / 간격 복습 예약
  └─ 아니오 → 짧은 예제 + 피드백 + 한 번 재시도
        │
        ▼
하루 종료 15~20분
[가장 약하고 중요한 3개만]
예제 → 수정·디버깅 → 독립 수행
        │
        ▼
다음 날 5~10분
답을 가리고 재현
        │
        ▼
주 1회 20~30분
[AI를 닫은 전이 점검]
비슷하지만 처음 보는 코드 설명·수정·작성
```

하루 8교시라면 교시 직후 3분은 최대 24분입니다. 하루 종료 복습은 모든 내용을 다시 다루지 않고 **가장 중요한 약점 3개**만 다룹니다. 이 시간은 연구가 보장한 최적값이 아니라, 8교시 피로와 지속 가능성을 고려한 첫 제품 가설입니다.

## 4. 라이브 수업 UX

### 4-1. 기본 화면은 “조용한 상태 표시”입니다

380px Chrome 사이드패널의 기본 상태에는 다음만 보입니다.

```text
┌──────────────────────────────────────┐
│ 10:32  듣는 중                 ● 저장│
│ IoC Container · 객체 생성 책임      │
│                                      │
│ 방금 잡힌 근거                       │
│ Tiro  12초 전 · Meet 4초 전          │
│ IDEA  ContextConfiguration.java      │
│                                      │
│ [못 들었어요] [이해 안 돼요]         │
│ [코드 흐름]   [선생님 근거]          │
└──────────────────────────────────────┘
```

- 전체 전사를 계속 흘려보내지 않습니다.
- 예쁜 애니메이션보다 최신 시각과 연결 상태를 분명히 보여 줍니다.
- Tiro·Meet·IntelliJ 중 하나가 오래됐으면 그대로 표시합니다.
- AI가 끊겨도 로컬 사건 기록은 계속됩니다.

### 4-2. 질문은 네 가지 “의도”로 먼저 표시합니다

| 버튼 | 뜻 | AI가 먼저 할 일 |
|---|---|---|
| 못 들었어요 | 말 자체를 놓침 | 직전 문장과 화면을 짧게 재구성 |
| 이해 안 돼요 | 들었지만 개념이 안 잡힘 | 한 문장 개념 설명 |
| 코드 흐름 | 어떤 값·객체가 어디로 가는지 모름 | 현재 코드에서 값 하나만 추적 |
| 선생님 근거 | AI 추측보다 수업 근거를 보고 싶음 | 타임스탬프·장면·코드 줄 제시 |

처음부터 빈 채팅창을 열면 질문을 작성하는 동안 수업을 더 놓칠 수 있습니다. 자유 질문은 두 번째 단계에 둡니다.

### 4-3. 답변은 세 층으로 제한합니다

```text
1층  결론 한 문장                자동 표시
2층  지금 코드에서 근거 1~2개    사용자가 펼침
3층  그림·예제·연습              수업 후로 저장
```

골든 시나리오의 첫 답은 다음 정도입니다.

> 직접 `new`를 쓰면 어떤 구현 객체를 만들지 현재 코드가 고정해서 결정하고, 컨테이너를 쓰면 그 선택 책임을 설정 바깥으로 옮길 수 있습니다.

그 아래에는 다음 행동만 둡니다.

```text
[현재 코드에서 보기]  [수업 뒤 자세히]  [수업으로 돌아가기]
```

### 4-4. 모든 답에는 근거 상태를 붙입니다

| 상태 | 뜻 | 예시 |
|---|---|---|
| 근거 충분 | 전사·화면·코드가 같은 내용을 가리킴 | Tiro 문장 + 설정 화면 + 현재 Java 줄 |
| 근거 일부 | 일부 문맥만 최신이거나 일치함 | Tiro는 최신이나 IntelliJ 파일은 5분 전 |
| 추론 | 수업 근거보다 일반 지식으로 답함 | “선생님 의도는 확인할 수 없지만 일반적으로…” |

이 표시는 AI가 맞는 척하는 것을 막는 장치이지, 신뢰도를 정확한 확률로 계산했다는 뜻은 아닙니다.

### 4-5. 라이브 개입의 상태도

```text
●
│ 수업 시작
▼
[조용히 듣는 중]
│
├─ 사용자가 표시 ───────────────▶ [문맥 봉인]
│                                  │
│                                  ├─ 근거 충분 → [한 문장 답]
│                                  └─ 근거 부족 → [제한 알림 + 가능한 답]
│                                                     │
│                                                     ▼
│                                             [수업으로 복귀]
│                                                     │
└─────────────────────────────────────────────────────┘

[조용히 듣는 중]
│ 교시 종료
▼
[3분 회상]
```

주기적으로 말을 거는 자동 튜터는 기본값에서 제외합니다. 자연스러운 휴지점이 검출되고 사용자가 허용한 경우에만 짧은 확인 질문을 제안합니다.

## 5. 교시 직후와 하루 종료 복습

### 5-1. 3분 Exit Ticket

`Exit Ticket`은 수업이 끝날 때 이해를 확인하는 아주 짧은 문제입니다. Classmate에서는 다음 세 칸으로 고정합니다.

```text
1. 이번 교시 핵심을 내 말 한 문장으로:
   [                                               ]

2. 값 또는 객체 하나가 어디서 어디로 갔나:
   [Application → ? → ? → 객체 필드]

3. 아직 남은 질문 하나:
   [                                               ]
```

중요한 순서:

```text
사용자 회상
    → 확신도 표시
    → AI 피드백
    → 수업 근거 확인
    → 한 번 재시도
```

회상·간격 두기는 여러 분야에서 장기 학습을 개선하지만, 복잡한 내용에서는 전이가 약해질 수 있습니다. 따라서 새롭고 어려운 Spring 절차를 아무 지원 없이 시험하지 않고, 먼저 충분한 예제·설명을 제공한 뒤 회상하게 합니다. [Carpenter, Pan & Butler 2022](https://www.nature.com/articles/s44159-022-00089-1)

### 5-2. 피드백은 시간대에 따라 달라집니다

디지털 피드백 메타분석에서는 평균적으로 긍정적인 효과가 있었지만, 즉시·지연 중 하나가 항상 우월하지 않았고 상세 피드백은 과부하를 만들 수도 있었습니다. [Digital feedback meta-analysis 2024](https://link.springer.com/article/10.1007/s10984-024-09501-4)

| 시점 | 피드백 길이 | 내용 |
|---|---|---|
| 라이브 | 한 문장 | 당장 오해를 막고 수업 복귀 |
| 교시 직후 | 3개 항목 | 어디가 맞고, 어디가 틀렸고, 다음에 무엇을 볼지 |
| 하루 종료 | 단계형 | 예제·추적·수정·디버깅 |
| 다음 날 | 정답 뒤 공개 | 먼저 독립 재현, 그 뒤 교정 |

### 5-3. 하루 종료에는 세 개만 깊게 다룹니다

선정 점수는 다음 정보로 만듭니다.

```text
우선순위
  = 수업 핵심도
  + 반복해서 막힌 횟수
  + 잘못 예측한 정도
  + 확신했지만 틀린 정도
  + 다음 프로젝트 단계와의 연결도
```

정확한 가중치는 PoC에서 정합니다. 첫 버전에서는 사람이 이유를 볼 수 있어야 합니다.

```text
오늘 1순위: 객체 생성 책임
이유: 두 번 질문함 · 확신 4/5였지만 추적 실패 · 다음 DI 실습의 전제
```

## 6. 프로그래밍 학습 사다리

### 6-1. 한 개념을 배우는 기본 진행

프로그래밍 worked example 연구와 디버깅 교육 문헌은 초보자가 완성 구조를 보고, 코드 흐름을 추적하고, 불완전 예제를 완성하며, 명시적 디버깅 절차를 배우는 방향을 지지합니다. [Muldner, Jennings & Chiarelli 2023](https://doi.org/10.1145/3560266), [Debugging education review 2024](https://doi.org/10.1145/3690652)

```text
0. 완성 결과를 먼저 본다
   “이 코드는 어떤 동작을 만들려고 존재하는가?”

1. 예측한다
   “이 줄 다음에 어떤 객체가 만들어질까?”

2. 값 하나를 끝까지 추적한다
   Application → 설정 메소드 → 반환 객체 → 주입받는 필드

3. 부분 구조를 완성한다
   코드 재배열 → 빈칸 → 불필요한 줄 찾기

4. 한 조건을 바꾼다
   구현체 변경 → 실행 결과 예측 → 실제 실행

5. 디버깅한다
   관찰 → 가설 → 한 가지 확인 → 직접 수정 → 이유 설명

6. 도움 없이 비슷한 기능을 쓴다

7. 다음 날 다시 만든다
```

Parsons 문제처럼 코드 조각을 재배열하는 활동은 처음부터 코드를 쓰는 것보다 부담이 낮고, 직접 작성으로 넘어가는 다리가 될 수 있습니다. 하지만 그것만 반복하면 독립 작성 능력을 확인할 수 없으므로 6·7단계를 생략하지 않습니다. [Multi-institutional Parsons study](https://scholars.duke.edu/publication/1616038)

2025년 프로그래밍 전용 연구에서는 AI 코드를 바로 모두 보여 주는 대신, 학습자가 다음 단계의 목적을 먼저 말하게 하는 `Lead-and-Reveal`과 실행값을 먼저 예상하게 하는 `Trace-and-Predict`가 학습과 사용 마찰의 균형에서 유망했습니다. 다만 N=82와 N=42의 짧은 알고리즘 과제이므로 장기 효과로 과장하지 않습니다. Classmate는 이 두 동작을 첫 PoC의 기본 상호작용으로 채택하고 다음 날 독립 수행으로 다시 검증합니다. [Kazemitabaar et al. IUI 2025](https://doi.org/10.1145/3708359.3712104)

### 6-2. 문제 먼저와 예제 먼저를 상황에 따라 고릅니다

문제 해결 후 설명하는 방식은 개념·전이에 평균 이점이 있었지만 절차 지식에서는 뚜렷한 이점이 없었습니다. [Sinha & Kapur 2021](https://journals.sagepub.com/doi/pdf/10.3102/00346543211019105)

| 상황 | 시작점 | 이유 |
|---|---|---|
| 처음 보는 복잡한 Spring 설정 | 완성 예제·부분 설명 | 작업 기억 부담을 낮춘다. |
| 방금 본 두 코드의 차이 | 짧은 예측·비교 | 기존 지식을 꺼내 구분하게 한다. |
| 이미 한 번 성공한 절차 | 빈칸·수정·디버깅 | 지원을 줄여 독립 수행으로 간다. |
| 다음 날 | 답을 가린 독립 재현 | 실제 보존을 확인한다. |

“먼저 실패하면 무조건 잘 배운다”와 “예제만 많이 보면 잘 배운다”를 모두 피합니다.

### 6-3. 힌트 사다리

```text
1단계  지금 무엇을 예상했는지 묻기
2단계  볼 파일·메소드·줄만 가리키기
3단계  관련 개념 한 문장
4단계  코드가 아닌 순서 설명
5단계  일부 예시 또는 빈칸
6단계  전체 답 — 사용자가 명시적으로 요청할 때
7단계  답을 닫고 유사 문제를 혼자 수행
```

AI가 전체 코드를 보여 줬다면 다음 중 하나를 수행하기 전에는 완료로 표시하지 않습니다.

- 핵심 줄을 자기 말로 설명
- 요구사항 하나를 바꿔 직접 수정
- 테스트를 실행하고 결과를 예측과 비교
- 다음 날 보지 않고 핵심 구조 재현

Anthropic의 2026년 공급사 연구에서는 AI를 사용한 소규모 집단이 새 Python 라이브러리 학습 퀴즈에서 낮은 결과를 보였고, 가장 큰 차이는 디버깅 영역이었습니다. 다만 N=52의 즉시 시험이므로 일반 법칙으로 말할 수 없습니다. 이 결과는 **AI 대리 디버깅을 기본값으로 두지 말아야 한다는 초기 경고**로만 사용합니다. [Anthropic 2026 coding skills study](https://www.anthropic.com/research/AI-assistance-coding-skills)

## 7. 간격 복습과 문제 선정

### 7-1. 고정된 “1·3·7일 법칙”은 쓰지 않습니다

최적 간격은 목표 보존 기간과 현재 기억 상태에 따라 달라집니다. 연구는 간격 두기의 일반적 이점을 지지하지만, 하나의 보편 일정은 지지하지 않습니다. [Cepeda et al. 2008](https://journals.sagepub.com/doi/full/10.1111/j.1467-9280.2008.02209.x), [Adaptive scheduling study 2020](https://www.nature.com/articles/s41539-020-00074-4)

첫 구현은 이해하기 쉬운 범위를 사용합니다.

```text
오늘 실패        → 같은 날 예제 뒤 재시도
교시 직후 성공   → 다음 날 첫 지연 확인
다음 날 성공     → 3~7일 범위에서 다음 확인
다시 성공        → 7~14일 범위 또는 프로젝트 전이 문제
실패              → 더 짧은 간격 + 더 작은 문제
```

일정은 다음 신호로 조절합니다.

| 신호 | 의미 | 다음 행동 |
|---|---|---|
| 정답 + 빠름 + 적절한 확신 | 비교적 안정 | 간격 늘리기 |
| 정답이나 매우 느림 | 아직 약함 | 간격 조금만 늘리기 |
| 오답이나 낮은 확신 | 모름을 알고 있음 | 예제 뒤 재학습 |
| 오답이나 높은 확신 | 위험한 오개념 | 우선 복습 + 구분 문제 |
| 같은 정의는 맞지만 코드 변형 실패 | 전이 부족 | 실제 코드 수정·디버깅 |

### 7-2. 모든 강의 내용을 카드로 만들지 않습니다

카드 또는 반복 문제 후보:

- 같은 오류를 두 번 겪음
- 실행 결과를 잘못 예측함
- 중요한 설계 선택의 이유를 설명하지 못함
- 자주 쓰지만 계속 잊는 명령·구조
- 사용자가 직접 “다시 보고 싶음”으로 표시

제외:

- 전체 강의 요약
- 긴 코드를 그대로 외우는 카드
- 검색하면 바로 나오는 세부 API 목록
- 아직 이해하지 못한 정의를 문장 빈칸으로 만든 카드

### 7-3. 섞어 연습하기는 “헷갈리는 것 구분”에만 씁니다

Interleaving은 평균적으로 도움이 되지만 연구 간 차이가 큽니다. 가장 타당한 용도는 서로 비슷해서 혼동하는 범주를 구분하는 것입니다. [Brunmair & Richter 2019](https://pubmed.ncbi.nlm.nih.gov/31556629/), [Interleaving systematic review](https://link.springer.com/article/10.1007/s10648-021-09613-w)

좋은 예:

```text
new 직접 생성  ↔ IoC 컨테이너 생성
상속            ↔ 인터페이스 구현
INNER JOIN      ↔ LEFT JOIN
Statement       ↔ PreparedStatement
필드 저장       ↔ 반환값
```

나쁜 예: Java 배열, Git 브랜치, Spring Bean, SQL 집계를 아무 이유 없이 무작위로 섞는 것.

## 8. 상세 HTML 복습자료 구조

하루 종일 수업한 결과가 PDF 한 장 요약으로 끝나면 안 됩니다. 그렇다고 전사 전체를 예쁘게 복사한 페이지도 안 됩니다. **상세 근거와 능동 연습을 함께 탐색하는 구조**가 필요합니다.

### 8-1. 정보 구조

```text
오늘의 학습 허브
│
├── 오늘의 지도
│   ├── 8교시 흐름
│   ├── 반복해서 막힌 개념
│   ├── 교시 사이의 연결
│   └── 오늘 다시 할 3개
│
├── 1교시 상세
│   ├── 수업 목표와 흐름
│   ├── 선생님 설명 타임라인
│   ├── Meet 장면 + 해당 전사
│   ├── IntelliJ 코드 상태
│   ├── 내 질문과 AI의 짧은 답
│   ├── 오개념·오류 기록
│   ├── 값 하나의 실행 흐름
│   ├── 직접 해보는 작은 변형
│   └── 근거 색인
│
├── 2~8교시 상세
│   └── 같은 골격, 내용에 맞는 표현
│
├── 능동 복습
│   ├── 답 가린 회상 카드
│   ├── 코드 추적
│   ├── 재배열·빈칸
│   ├── 수정·디버깅
│   └── 독립 전이 문제
│
└── 증거와 진행
    ├── 타임스탬프·전사·장면·코드
    ├── AI 근거 충분/일부/추론
    └── 무AI 수행 기록
```

### 8-2. 멀티미디어 배치 원칙

멀티미디어 학습 연구는 텍스트·그림 결합, 핵심 신호 표시, 불필요한 장식 제거, 구간 나누기의 평균 이점을 지지하지만 조건에 따른 차이도 큽니다. [Mayer corpus meta-analysis 2025](https://www.sciencedirect.com/science/article/pii/S1747938X25000673), [Multimedia learning review 2022](https://link.springer.com/article/10.1186/s40561-022-00200-2)

한 사건 카드에는 서로 관련된 것만 가까이 둡니다.

```text
10:32:18 · “객체 생성 책임”
┌─────────────────────┬─────────────────────┐
│ Meet 장면           │ IntelliJ 핵심 줄     │
│ 관련 부분만 자름    │ 현재 줄만 강조       │
├─────────────────────┴─────────────────────┤
│ 선생님 전사 2~4문장                       │
├───────────────────────────────────────────┤
│ 내 질문 → 한 문장 답 → 내가 고친 설명     │
└───────────────────────────────────────────┘
```

피할 것:

- 같은 내용을 음성·전체 전사·긴 AI 설명으로 동시에 중복
- 관련 없는 시네마틱 장식과 긴 전환 효과
- 동일한 크기의 카드 수십 개
- 근거 없이 만든 매끈한 도식
- 사용자가 무엇을 해야 하는지 없는 읽기 전용 페이지

`CINEMATIC-DECK-PLAYBOOK.md`는 이야기 흐름·장면 설계·시각 검증 원칙을 선택적으로 사용할 수 있지만, 모든 교시에 같은 미학을 강제하지 않습니다. 코드 실습형, 관계 도해형, 이야기형, 시험 복습형 중 내용에 맞는 렌더러를 고릅니다.

## 9. AI 튜터의 행동 규칙

### 9-1. 논리 역할

첫 PoC에서는 네 역할을 별도 프로세스로 만들 필요가 없습니다. 한 프로그램 안의 명확한 책임으로 둡니다.

| 역할 | 책임 | 하지 않는 일 |
|---|---|---|
| Context Curator | 질문 시점의 전사·화면·코드를 묶고 최신성을 표시 | 없는 근거를 채워 넣지 않음 |
| Live Tutor | 한 문장 결론과 최소 힌트 제공 | 수업 중 긴 강의 시작 안 함 |
| Lesson Editor | 교시 흐름·질문·오류·근거를 상세 구조로 정리 | 한 장 요약으로 압축 안 함 |
| Practice Coach | 회상·추적·수정·디버깅·간격 일정 제어 | AI 답을 읽은 것만으로 완료 처리 안 함 |

### 9-2. 상태를 앱이 통제합니다

```text
[CAPTURE]
전사·화면·코드 사건 기록
    │ 사용자 질문
    ▼
[ANSWER_MINIMAL]
결론 한 문장
    │
    ├─ “수업으로” → [CAPTURE]
    └─ “자세히”   → [SAVE_FOR_REVIEW]

[EXIT_RECALL]
사용자가 먼저 답함
    │
    ▼
[FEEDBACK]
근거와 오류를 보여 줌
    │
    ▼
[FADE_SUPPORT]
예제 → 부분 완성 → 수정 → 독립 수행
    │
    ▼
[DELAYED_CHECK]
다음 날 AI 없이 확인
```

모델에게 “소크라테스식 튜터가 되어 줘”라고만 말하지 않습니다. 앱이 현재 상태, 보여도 되는 힌트 단계, 정답 공개 여부, 완료 조건을 전달합니다.

또한 설명이 자연스럽다는 이유만으로 맞다고 판정하지 않습니다. LLM 답변의 오류와 장황함을 분석한 연구, 그리고 코드 출처가 AI임을 알았을 때 개발자가 더 많이 검증했다는 소규모 연구는 **출처와 검증 상태를 화면에 드러낼 필요**를 지지합니다. 오래된 모델·작은 표본 결과이므로 현재 모델의 정확한 오류율로 인용하지 않고, 검증 UI의 필요성으로만 사용합니다. [Kabir et al. CHI 2024](https://doi.org/10.1145/3613904.3642596), [Tang et al. VL/HCC 2024](https://doi.org/10.1109/VL/HCC60511.2024.00015)

코드 또는 코드 설명에는 다음 상태를 붙입니다.

```text
AI 생성
├─ 수업 근거 연결됨 / 없음
├─ 컴파일 확인됨 / 미확인
├─ 테스트 확인됨 / 미확인
└─ 버전 주장은 공식 문서 확인됨 / 미확인
```

### 9-3. 학습 모드와 제작 모드를 분리합니다

| 모드 | AI 기본 행동 | 사용자 책임 |
|---|---|---|
| 학습 모드 | 질문·힌트·부분 예시·근거 제시 | 예측·직접 수정·실행·설명 |
| 제작 모드 | 전체 코드 생성·수정 가능 | 요구사항·테스트·보안·코드 소유권 검토 |

IntelliJ 연결의 라이브 기본값은 읽기 전용입니다. 수업 중에는 파일 수정·명령 실행·터미널 조작을 하지 않습니다. 제작 모드는 수업 뒤 사용자가 명시적으로 전환할 때만 엽니다.

## 10. 성공 지표와 2주 PoC

### 10-1. 다섯 단계 성취 지표

| 단계 | 확인 질문 | 증거 |
|---|---|---|
| 1. 예측 | 실행 전에 결과를 맞혔나? | 예측과 실제 결과 |
| 2. 추적 | 값·객체 하나를 처음부터 끝까지 따라갔나? | 단계별 경로 설명 |
| 3. 설명 | 왜 그런 구조인지 자기 말로 말했나? | 한 문장·음성·그림 |
| 4. 전이 | 도움 없이 비슷한 기능을 만들거나 고쳤나? | 새 코드·테스트·디버깅 |
| 5. 보존 | 다음 날 다시 해냈나? | 답을 가린 지연 수행 |

다음은 보조 지표일 뿐 성공 지표가 아닙니다.

- 생성된 HTML 수
- 노트 글자 수
- 모델 호출 횟수
- 앱에 머문 시간
- “이해했어요” 버튼 수

### 10-2. 라이브 집중 지표

| 지표 | 측정 방법 | 성공 방향 |
|---|---|---|
| 질문 해결 시간 | 표시부터 수업 복귀까지 | 짧아짐 |
| 답변 중 놓친 수업 구간 | 답변을 보는 동안의 다음 내용 회상 | 줄어듦 |
| 근거 묶음 성공률 | 전사·화면·코드가 같은 사건인지 사람 검수 | 높아짐 |
| 잘못 확정한 답 | 근거 부족인데 단정한 비율 | 줄어듦 |
| 자동 개입 거부율 | 먼저 띄운 제안을 닫은 비율 | 낮아짐 |

### 10-3. 2주 PoC

#### 첫 주: 흐름과 부담 검증

| 날 | 조건 | 확인할 것 |
|---|---|---|
| 1~2일 | 시점 저장만, 즉시 AI 답 없음 | 질문을 잃지 않고 수업을 따라가는가? |
| 3~4일 | 한 문장 즉시 답 | 다음 설명 누락 없이 이해 회복이 빨라지는가? |
| 5일 | 일부 질문에 상세 즉시 답 | 실제로 더 놓치는지 비교 |

매일 공통:

- 교시 직후 3분 회상 완료율
- 수업 중 놓친 느낌 1~5
- 질문 해결 시간
- 다음 날 핵심 3개 재현

#### 둘째 주: 학습 사다리 검증

같은 난이도의 개념을 번갈아 비교합니다.

| 조건 A | 조건 B |
|---|---|
| AI 요약 읽기 + 자유 질문 | 사용자 회상 → 힌트 사다리 → 코드 변형 → 다음 날 재현 |

확인:

- 다음 날 설명 정확도
- 처음 보는 유사 코드의 출력 예측
- 도움 없이 한 부분 수정
- 디버깅 가설의 질
- 총 학습 시간과 피로도

표본은 우선 사용자 한 명이므로 통계적 제품 효과를 주장하지 않습니다. 대신 어느 흐름이 실제 생활에서 지속 가능하고, 어떤 실패가 반복되는지 찾는 **개인 내 PoC**로 사용합니다. 친구가 참여하면 같은 절차를 반복하되 결과를 독립 표본처럼 과장하지 않습니다.

### 10-4. 중단·수정 조건

- 한 문장 답도 다음 설명을 더 놓치게 하면 라이브 답을 없애고 시점 저장만 남깁니다.
- 교시 직후 3분 수행률이 계속 낮으면 세 칸 중 하나만 필수로 줄입니다.
- HTML을 읽기만 하고 코드 행동으로 이어지지 않으면 홈에서 요약보다 “지금 할 한 문제”를 먼저 보여 줍니다.
- AI 사용 조건이 다음 날 독립 수행을 낮추면 답 공개를 늦추고 힌트 단계를 더 엄격히 합니다.
- 근거 묶음 오류가 높으면 멀티모달 답변보다 사용자가 장면을 확인하는 UI를 먼저 고칩니다.

## 11. 확정·가설·금지 항목

### 연구 근거와 사용자 요구로 기본값에 반영

- 라이브 기본 상태는 조용합니다.
- 상세 설명은 수업 뒤로 미룹니다.
- 사용자가 먼저 회상·예측한 뒤 피드백합니다.
- 예제 지원을 단계적으로 줄여 독립 수행과 지연 재현으로 끝냅니다.
- 비슷해서 헷갈리는 개념만 섞어 연습합니다.
- 전사·화면·코드·AI 설명의 출처와 최신성을 표시합니다.
- 노트 분량보다 행동 증거로 숙달을 판단합니다.
- 사용자를 시각형·청각형 같은 학습 스타일로 고정하지 않습니다. 학습 스타일 matching 연구는 질과 결과가 불안정합니다. [Learning styles meta-analysis 2024](https://doi.org/10.3389/fpsyg.2024.1428732)

### 제품 PoC로 검증할 가설

- 380px 패널의 한 문장 답이 시점 저장만 하는 것보다 실제로 도움이 됩니다.
- Tiro+Meet+IntelliJ 결합이 전사 단독보다 기술 용어와 코드 맥락 오류를 줄입니다.
- 교시마다 3분 회상이 8교시 일정에서도 지속 가능합니다.
- 하루 약점 3개 제한이 누락감 없이 학습 행동을 늘립니다.
- 상세 HTML의 사건 카드가 전체 녹화 재시청보다 실제 복습 시작률을 높입니다.
- Codex와 Claude가 같은 상태·힌트 계약 아래 비슷한 품질을 냅니다.

### 만들지 않을 것

- 하루 8시간 계속 생각하고 먼저 말하는 AI
- 전체 전사를 채팅창에 계속 흘리는 UI
- 수업 내용을 PDF 한 장으로만 줄이는 결과
- 모든 내용을 자동으로 카드화하는 기능
- 읽기·대화 시간을 숙달로 계산하는 대시보드
- 사용자의 코드 시도 전에 바로 전체 답을 쓰는 학습 모드
- 예쁜 노트 생성을 실제 공부보다 앞세우는 UX
- 특정 `1·3·7일` 일정을 과학적 보장처럼 광고하는 기능
- 사용자를 하나의 학습 스타일로 분류하는 기능

## 최종 제품 원칙

```text
수업 중에는 주의를 지킨다.
수업 직후에는 기억을 꺼낸다.
복습할 때는 코드를 직접 다룬다.
도움은 점차 줄인다.
다음 날 혼자 해내는지 확인한다.
모든 AI 답은 실제 수업 근거로 돌아갈 수 있게 한다.
```

이 원칙을 지키면 Corthex Classmate는 “녹음·요약 도구”와 분명히 달라집니다. 강의를 더 많이 저장하는 것이 아니라, **놓친 순간을 복구하고 저장된 수업을 독립 수행으로 변환하는 시스템**이 됩니다.
